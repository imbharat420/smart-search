# Document review — TravelIQ Search Engine Overview

| | |
|---|---|
| Document reviewed | `docs/TravelIQ-Search-Engine-Overview.docx`, 8 sections, approx. 1,450 words |
| Version reviewed | the copy in this repository, undated and unversioned (finding G-02) |
| Reviewed against | the POC built in this sprint (`backend/app/*`, `src/*`) and UK travel-retail practice |
| Review date | 29 July 2026 |
| Reviewer | Delivery lead, with input from solution architecture and security |

The overview is a strong sales document: the problem statement in section 1 is accurate about how
travel search actually fails, and the four-step install narrative in section 2 is the right shape for
an installable product. It is not yet a specification. Nothing in it is testable, several
capabilities contradict each other, and the parts a UK travel client's legal and IT functions will
challenge first — financial protection, trade pricing, consent, roles — are either absent or asserted
in one line.

This review lists 27 findings. Severity is delivery risk, not writing quality:
**High** = will change architecture, price or go-live date if left unresolved;
**Medium** = will cause rework or a failed sign-off;
**Low** = wording or completeness.

## A. Stack and architecture contradictions

| ID | The document says | Issue | Why it matters | Resolution | Owner |
|---|---|---|---|---|---|
| **A-01** High (§4) | "Search engine \| Index storage, keyword and semantic search, filtering and ranking \| Algolia" | Names a specific hosted third party as the search engine. This POC implements retrieval with PostgreSQL full-text search plus an in-process embedding index (`backend/app/rag.py`, `backend/sql/indexes.sql`) and no Algolia account exists. | Algolia is priced per search operation and per record; at 250k searches a month that is a recurring line item nobody has budgeted, plus a second data-processing location to declare. Choosing it also fixes the ranking model, the facet semantics and the security model — all three are load-bearing elsewhere in the document. | Restate section 4 as "Search engine: pluggable". Ship the POC on Postgres FTS + in-process embeddings, and present two costed production options: (a) Algolia, (b) Postgres FTS + `pgvector` in the client's own database. Record the decision with its cost model before Release 3. | Solution Architect |
| **A-02** High (§4) | "Frontend \| ... \| Next.js / React"; "Backend API \| ... \| NestJS"; "Data pipeline \| ... \| NestJS workers" | The delivered POC is Vite + React 19 + React Router 6 on the front end and FastAPI (Python 3.13) on the back end, with the ingestion pipeline as an in-request function (`backend/app/ingest.py`), not a worker. | Two different stacks cannot both be estimated. The Next.js/NestJS figure implies a Node team; the POC implies a Python team plus a separate SSR decision. Left unresolved, the client budgets one and receives the other. | Separate "POC stack" from "production target stack" in one table, and itemise the delta — SSR shell, worker queue, job scheduler — as costed work rather than a footnote. Done for the POC side in `docs/architecture.md`. | Solution Architect + Delivery Lead |
| **A-03** High (§8 vs §4) | "No lock-in \| The platform is installed in your own application, with your own data and your own search account." | Directly contradicted by A-01. An Algolia index is not the client's data in any portable sense: leaving it requires a full reindex plus a rewrite of every query, facet and ranking rule, because those are Algolia-shaped. | This is a stated purchase benefit. If a client buys on "no lock-in" and later discovers the ranking rules live in a third-party dashboard, that is a commercial dispute, not a technical one. | Either qualify the benefit ("your catalogue and configuration remain in your own PostgreSQL; the search index is a rebuildable derivative") or take the Postgres + `pgvector` option, where the claim is literally true. | Commercial Lead |

## B. Performance claims that cannot be measured

| ID | The document says | Issue | Why it matters | Resolution | Owner |
|---|---|---|---|---|---|
| **B-01** High (§5.1) | "The search engine is queried directly from the browser using a short-lived secure key, returning results in well under a second." | No percentile, no scope and no measurement point. It is not stated whether the second includes the AI parse in the preceding step, the network, or only the index lookup. "Well under" is not a number. | This is the sentence a client will quote back during acceptance. As written, both sides can be right and neither can prove it. The scope question is decisive: the AI parse is a language-model round trip, which on the providers wired into `llm.py` runs 300–2,000 ms — so the end-to-end figure fails while the index lookup passes. | Split the budget and name the measurement point, as now specified in `docs/scope-and-limitations.md`: index + rank p95 ≤ 400 ms server-side; NL parse p95 ≤ 800 ms with an 8 s hard ceiling and heuristic fallback; cached parse p95 ≤ 250 ms end-to-end. Measure server-side from the `tookMs` field already returned in every `SearchResponse`, and client-side from RUM. | Tech Lead |
| **B-02** Medium (§5.1) | "Repeated queries are cached and resolved instantly." | No cache key definition, no TTL, no invalidation. "Instantly" is undefined, and it is not stated whether the cache holds the parse, the result set, or both. | A result-set cache that survives a synonym or promotion change serves stale merchandising, which is exactly the class of bug the admin panel exists to prevent. A parse cache is safe; a result cache is not, and the document does not distinguish them. | Cache the parse only. Key on the query lowercased with punctuation and repeated whitespace collapsed; LRU 256 entries; flush on any synonym or search-config write. The POC caches the parse in `nlq.py` (LRU 256, no TTL) and never caches result sets. State the 24 h TTL and the write-triggered flush as production requirements. | Tech Lead |
| **B-03** Medium (§5.2) | "The final record is saved to the database and indexed for search, typically within a minute." | "Typically" with no percentile, no behaviour under queue depth, and no figure for the scheduled full sync ("a scheduled full sync as a safety net") against a catalogue of stated size. | Freshness is a commercial guarantee in travel: a sold-out departure still showing as available produces a refund and a complaint. Without a lag metric there is no way to know the guarantee is being met. | Target p95 webhook-to-searchable ≤ 60 s, full sync completing inside a stated overnight window for a stated record count, and both surfaced as a lag figure on the admin Data sources tab. The POC ingests synchronously and rebuilds the embedding index at startup only — trips ingested after startup score lexically until restart. Named as a limitation. | Tech Lead + Product Ops |

## C. Data model gaps

| ID | The document says | Issue | Why it matters | Resolution | Owner |
|---|---|---|---|---|---|
| **C-01** High (§3.1, §7) | "somewhere warm in november under 1200 direct flights → Maximum price: 1,200"; "Localised URL structures are supported for multi-country websites." | Multi-country websites are promised but there is no currency model anywhere in the document. Price appears as a bare number. Nothing states where the FX rate comes from, how rounding and psychological price points are handled, whether a market can override a price, or how price facet buckets behave across currencies. | Converting at query time breaks facet counts (a "under £1,200" bucket is not "under €1,400" for the same set) and breaks price sorting stability. Retrofitting currency after the index and the facet buckets are built is a schema change plus a reindex plus an admin-panel change. | Model money as amount + ISO 4217 currency, with a per-market price list rather than runtime conversion; define facet buckets per currency; state the FX source and refresh cadence if any conversion is kept. The POC is GBP-only throughout, deliberately and visibly (`money()` in `src/lib/format.ts`, `currency: 'GBP'` on `Trip`). | Business Analyst + Solution Architect |
| **C-02** High (§3.2, §7) | "Typo tolerance and multi-language support, configured per market."; "Localised URL structures are supported for multi-country websites." | Multi-language search is promised with no locale dimension in the data model: no translated title, summary or description; no per-locale slug; no per-locale synonym scope; no hreflang; no statement of whether the language of the query and the language of the content are allowed to differ. | "Configured per market" reads like a settings change; it is a translation pipeline, a locale-keyed schema and an SEO structure. This is the single largest hidden cost in the document. | Add `trip_translations(trip_id, locale, ...)` with a fallback chain, a locale column on synonyms, locale-prefixed routes and an hreflang set. The POC ships a single `en-GB` market; `Synonym.market` is stored but not applied at query time, and `rag.py` says so in a comment. Multi-locale scoped out and costed separately. | Business Analyst + Solution Architect |
| **C-03** Medium (§3.2) | "Location-based search, including 'near me' and radius search." | Ambiguous for a travel product and unspecified operationally. It is not stated whether the radius applies to the traveller's departure airport or to points of interest at the destination — for a holiday in Iceland sold to a traveller in Leeds, both readings are plausible and they need different data. No geocoding provider, no default radius, no units (miles or kilometres for a multi-country product), no permission-denied fallback. | The two readings are different features with different data requirements. Building the wrong one is a full iteration lost. Units matter: a UK site quoting kilometres reads wrong, a European site quoting miles reads wrong. | Split into two named features: departure-airport filter (UK regional airports) and destination POI proximity. Define units per market with miles for en-GB, a 25-mile default, and an explicit fallback to a typed location when geolocation is denied. The POC implements POI proximity in miles on `/discover` with a static map. | Business Analyst |

## D. Security, compliance and commercial rules

| ID | The document says | Issue | Why it matters | Resolution | Owner |
|---|---|---|---|---|---|
| **D-01** High (§6) | "Admin access is role-based, with configuration changes recorded in an audit log." | One sentence covering the entire authentication and authorisation model. No roles are enumerated, no permission matrix exists, and there is no statement on SSO, MFA, session lifetime, password policy, invitation and de-provisioning, or which actions are audited. | This is the first item a client's IT security function reviews, and an un-answered access model blocks go-live regardless of how good the search is. It is also where "marketing independence" (§8) creates risk: someone who can hide products can hide revenue. | Define four roles — Owner, Admin, Merchandiser, Analyst — with an explicit permission matrix per admin surface; OIDC SSO against the client's IdP; MFA mandatory on Owner and Admin; audit every write with actor, before and after values. The POC has **no authentication at all**: `/admin` is open and admin routes accept an `X-Actor` header used only to attribute the audit entry. Stated in `docs/scope-and-limitations.md` and visible in the admin UI copy. | Security Lead + Business Analyst |
| **D-02** High (§6 vs §5.1) | "Trade-only or agency pricing can be locked so it cannot be accessed by public visitors." against "The search engine is queried directly from the browser using a short-lived secure key" and "Search requests do not pass through your application server." | These cannot all hold as written. Enforcing trade pricing requires knowing who the visitor is, which requires an authenticated session and a server call to mint an audience-scoped key — a server round trip the same section says does not happen. The document never introduces trade identity, and never says whether trade prices are excluded from the public index or merely hidden at query time. | Hiding a field at query time is not a control: if the trade price is in the public index, it is retrievable. A leaked agency rate card is a commercial incident with contractual consequences for the client's supplier agreements. | Build two indices, or one index with the trade fields absent from the public build; mint the browser key server-side per authenticated session with the audience baked in; never rely on a query-time filter for a commercial secret. Document the login round trip honestly as the one server call in the path. Out of scope for the POC — there is no trade tier and no auth. | Solution Architect + Commercial Lead |
| **D-03** High (§6, §3.5) | "Commercially sensitive fields such as margin can influence ranking without ever being visible to the browser." | Two problems. Technically, with browser-direct search the ranking configuration and any custom ranking attribute are usually readable from the response or the index settings, so "never visible" needs a mechanism: margin folded into a precomputed, non-reversible score at index time. Commercially, the document never mentions that ranking influenced by the seller's own margin is a paid-placement question under UK consumer law. | CMA guidance on ranking transparency (and the Digital Markets, Competition and Consumers Act regime) expects material ranking parameters to be disclosed to consumers. Silent margin weighting on a UK travel site is a regulatory exposure the document creates and does not flag. | Precompute a single opaque `ranking_score` at index time so margin never leaves the server; add a plain-English ranking disclosure and label promoted results. The POC's promotions are pin, boost and hide, and every affected result carries a visible reason — `"boosted in merchandising"` or `"pinned in merchandising"` in `matchedOn` (`backend/app/rag.py`). That visibility is deliberate and is the disclosure mechanism. Legal review required before any margin weighting ships. | Security Lead + Legal + Commercial Lead |
| **D-04** Medium (§6, §3.5) | "Analytics tracking is gated behind your cookie consent platform, such as Cookiebot. Search itself works without consent; only tracking and personalisation require it." against "Every search, click and booking is recorded and linked back to the search that produced it." | The two statements are not reconciled. If click and booking recording is consent-gated but searches are counted server-side, then CTR and conversion have a server-side numerator problem: the denominator counts all searches, the numerator counts only consenting visitors. The document also does not say which tier the raw search log belongs to. | Every number on the analytics tab is wrong by the consent rate, silently. A 60% consent rate makes a genuine 4% CTR read as 2.4%, and a merchandiser will "fix" a ranking problem that does not exist. | Define two tiers: (1) server-side aggregate search logging with no identifiers and no cookie, retained under legitimate interest; (2) consented behavioural events. Publish the consent rate next to CTR and conversion so the denominator is honest, or scale the numerator by it and label the figure as estimated. The POC has no consent platform, logs every event unconditionally, and ships a seeded analytics window — stated in the UI. | Data Protection Officer + Tech Lead |
| **D-05** Medium (§6) | "No personal data is stored in the search index." and "Data location can be set to meet your regulatory requirements." | True and beside the point. The risk is not the index: it is `search_queries`, which stores raw query text. Travellers type names, ages, disabilities and medical conditions into travel search boxes ("wheelchair accessible for my mother Jean"). That is personal and sometimes special-category data, held in analytics with no retention period, no scrubbing and no subject-access route stated. | The sentence as written gives the client false comfort during a DPIA. A regulator asks about the query log, not the index. | Add a retention policy (raw query text 90 days, aggregated indefinitely), a scrubbing pass over query text before storage, a documented subject-access and erasure path, and a DPIA covering the analytics store. The POC stores raw query text indefinitely with no scrubbing. | Data Protection Officer |
| **D-06** Medium (§5.1) | "Search requests do not pass through your application server. This keeps results fast and means peak search traffic does not put load on your website infrastructure." | The trade-off is stated as pure upside. A browser-direct search endpoint is also directly abusable: it is a public, keyed, unrate-limited read over the entire catalogue, which is a competitor's price-scraping tool. Nothing in the document mentions rate limiting, key rotation or abuse detection. | For a hosted search engine this is also a cost-control matter, since search operations are billed. An unthrottled public endpoint is an unbounded bill. | Add per-key and per-IP rate limits with a stated ceiling, short key TTL with rotation, and anomaly alerting on operations per key. State the cost per 1,000 search operations in the commercial pack. | Security Lead + Tech Lead |

## E. Search quality and operations

| ID | The document says | Issue | Why it matters | Resolution | Owner |
|---|---|---|---|---|---|
| **E-01** Medium (§5.2, §3.3) | "Confident matches are merged using your configured rules. Uncertain matches go to a review queue and are never published automatically." | "Confident" and "uncertain" are never quantified, and the review queue has no owner, no SLA, no ageing behaviour and no escalation. There is also no way to undo a wrong auto-merge. | A queue with no SLA silently becomes a backlog, and a backlogged merge candidate is a duplicate holiday on the results page or a price that never updates. An un-undoable auto-merge is worse: two holidays fused into one record, with one supplier's price on another supplier's product. | Publish the thresholds; name a merchandising owner; SLA of 1 business day for candidates that affect price or availability and 5 business days otherwise; alert on any candidate older than 48 h; queue depth on the admin dashboard. Add an unmerge action that restores both source records. The POC implements `AUTO_MERGE = 0.86` and `REVIEW_FLOOR = 0.60` (`backend/app/ingest.py`), four weighted match signals, a hard cap of 0.55 for records in different destinations, and an `audit_log` entry per merge. **Unmerge is not implemented** and is named as out of scope. | Head of Product Ops |
| **E-02** Medium (§3.3, §5.2) | "It is matched against existing products to identify the same product from a different source." | No matching signals, no weights, no precision or recall target, and no statement of what an acceptable false-merge rate is. The reader cannot tell whether matching is title-based, identifier-based or something else. | Match quality is the whole value of the "one complete catalogue" benefit in §8, and it is the one thing that cannot be judged after go-live without a labelled test set. Without a target there is no basis for acceptance. | Publish the signals and weights, and set targets: zero false auto-merges on a labelled fixture, review-band rate ≤ 20% of inbound records. The POC scores title similarity 0.50, destination 0.25, duration 0.15 and price 0.10, redistributing the weight of any signal missing on one side, and records the human-readable reasons the editor sees in the queue. | Tech Lead |
| **E-03** Medium (§3.5) | "Results improve automatically over time based on what visitors actually choose." | An unspecified learning loop. No signal definition, no decay, no cap on its contribution, no cold-start behaviour for a new product, no stated precedence against a manual pin, and no holdout to prove it helps rather than entrenches. | A naive click-signal loop makes the top result permanently the top result and buries new inventory — the opposite of the "one complete catalogue" benefit. It also collides with §3.4 promotion: if the model and the merchandiser disagree, one must lose, and nobody has said which. | Specify it as a decayed click-signal boost with a capped contribution to the final score, a new-product exploration allowance, explicit precedence **below** manual pins, and a permanent holdout that reports the loop's actual lift. Out of scope for the POC; the POC's ranking is deterministic and explainable, which is the right first step. | Tech Lead + Head of Product Ops |
| **E-04** Medium (§3.5) | "Changes can be tested against live traffic and judged on conversion before being kept." | No assignment unit, no metric definition, no minimum detectable effect and no traffic threshold. Travel booking conversion is typically 1–2%; detecting a 10% relative change at that base rate needs roughly 100k–150k sessions per arm. | Mid-market travel sites do not have that traffic on a search page, so the promise as written is statistically unreachable and every test will read "no significant difference". That is a credibility problem at the first review meeting. | Keep experimentation but state the traffic prerequisite; use CTR to first click as the primary metric (base rate 20–40%, so tests conclude in days) with conversion as a guardrail; define the assignment unit as the visitor, sticky across the session. | Analytics Lead |
| **E-05** Low (§3.4) | "Appearance \| Widget layout, result card design, fonts and spacing, and placement of search sections." | An unbounded theming surface. Free control of fonts, spacing and layout means the delivered design system, its accessibility contrast pairs and its Core Web Vitals figures can all be invalidated by a non-technical user on a Friday afternoon. | Both a support cost and a broken warranty: any performance or accessibility guarantee is void the moment layout is arbitrary. | Constrain it to a token set: brand colour, radius, density, logo, and a choice of three tested result-card presets. Validate contrast on save and refuse combinations below 4.5:1. The POC exposes search setup, promotion, synonyms, sources and analytics; the Appearance tab is deliberately not built, and the admin UI says so. | Design Lead |

## What this POC deliberately does differently from the document

Not every divergence is a defect. Three were chosen:

| Document | POC | Why |
|---|---|---|
| Algolia as the search engine | PostgreSQL FTS + in-process embedding index with a lexical fallback | Runs on a laptop with no third-party account, keeps the "no lock-in" claim true, and proves the retrieval behaviour without a per-search bill. |
| Next.js SSR | Vite client-rendered SPA with filters in the URL and numbered pagination | SSR is real work with real infrastructure; faking it would hide the cost. The SEO-shaped decisions that are cheap now — readable URLs, numbered pagination, per-page metadata, structured data — are all in, and the SSR delta is costed in `docs/architecture.md`. |
| PostgreSQL as a hard requirement | PostgreSQL when `DATABASE_URL` is set and reachable, otherwise an in-memory seeded catalogue, with `/health` reporting which | Mirrors the document's own fallback philosophy from §3.1 and makes the POC demonstrable anywhere. The Postgres schema is complete and reviewable in `backend/sql/schema.sql`. |
